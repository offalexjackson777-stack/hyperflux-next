This page lists how the HyperFlux repository is set up on GitHub: workflows, required
checks, issue forms, Discussions, and security settings, for maintainers and for
contributors who want to know what runs on their pull request. Releases, tags, and
the signed Arch repository are published by the maintainer, not by a GitHub workflow.

## Workflows

| Workflow | Trigger | Network during verification | Hardware access | Output |
| --- | --- | --- | --- | --- |
| Verification | Pull requests, main, manual | None | None | Source-bound fast evidence |
| Full verification | Pull request, weekly, or manual | None | None | Source-bound full evidence |
| CodeQL | Pull requests, main, weekly | GitHub service only | None | C/C++ and Python analysis |
| Dependency review | Pull requests | GitHub service only | None | Dependency policy decision |
| Kernel canary | Weekly or manual | Arch mirrors, kernel.org, and the pinned app sources | None | Driver builds against coming kernels; never required for merging |
| Distribution packages | Pull requests, weekly, or manual | Ubuntu, Debian, Fedora and openSUSE archives for the check tools, and OpenRazer's openSUSE Build Service repository | None | Ubuntu 26.10 and Debian 14 `.deb` files and Fedora 44 and openSUSE Tumbleweed `.rpm` files, checked and not published; required for merging into `main` |

The development image may use the network only to fetch its pinned packages and tools while it is built. The pinned app sources are prepared before the checks start. Every check then runs in the pinned image with `--network none`, no devices, no privileges, no extra capabilities, and write access only to the checkout.

The kernel canary is the one deliberate exception, because its purpose is to follow kernels that move after the image is pinned. It starts from the same digest-pinned Arch base image and installs this week's `linux-headers` and `linux-lts-headers`. It also stages the next Arch kernel from `core-testing`, when there is one, and the newest mainline tag from kernel.org prepared with `modules_prepare`. Then `./hfx kernel-canary` builds the HyperFlux driver and the patched OpenRazer driver against each kernel with `W=1`. It only compiles: nothing is loaded and no device is touched. Its result never gates a merge. A failure is an early warning that a kernel interface changes before it reaches users.

The distribution packages workflow reaches outside the pinned image like the kernel canary, but unlike it, it is required for merging into `main`. It runs every week, when started by hand, and on every pull request. A small first job, `Packaging changes`, lists the files the pull request changes. Every pull request into `main` runs the `Distribution packages` job. A pull request into another branch runs it only when it changes what the packages are made from or how they are checked: the packaging inputs, the driver sources, the package tools and their schemas, or the workflow itself. Otherwise the job reports as skipped, which GitHub counts as passing. If the first job fails, the packages are checked anyway, so a broken first job never lets the check pass unseen. A new push to the same pull request cancels the run still going. It builds the package artifacts once, offline in the pinned development image, exactly as the Arch packages are built. Then, for Ubuntu 26.10, Debian 14, Fedora 44 and openSUSE Tumbleweed in turn, it starts that release's digest-pinned image without extra privileges and installs the check tools from the release's own archive. In that container `./hfx package distro` turns the artifacts into the Core packages `hyperflux-next-dkms` and `hyperflux-next-linux` and the Full packages `hyperflux-next-openrazer-driver-dkms` and `hyperflux-next-full`, which leave out the OpenRGB plugin because no OpenRGB those releases ship can load it. On Ubuntu and Debian the workflow inspects every `.deb` file with `dpkg-deb`, fails on any `lintian` error, and installs Core and then Full with `apt-get` while `policy-rc.d` refuses every service start. With Full installed it adds the release's own `openrazer-daemon` and `python3-openrazer`, and fails if apt pulls in the release's OpenRazer driver package instead of the HyperFlux one. On Fedora and openSUSE `rpmbuild` builds every `.rpm` file from one generated spec inside the release image, so the host never needs RPM tools. The workflow prints each header, file list and scriptlet with `rpm`, fails on any `rpmlint` error except those the generated `rpmlint` configuration accepts by name and reason, and installs Core and then Full with `dnf` or `zypper`. Those releases do not ship OpenRazer, so with Full installed the workflow adds OpenRazer's own `hardware:razer` repository from the openSUSE Build Service and installs its `openrazer-daemon` and `python3-openrazer`. It trusts the repository's signing key only when the key's fingerprint matches the one pinned in the generator, keeps package signature checks on, checks that both packages carry that key's signature, and fails if OpenRazer's own driver package is installed instead of the HyperFlux one. The scriptlets only register and build the DKMS sources and never enable or start a unit, which the workflow checks under `/etc/systemd`. Then `dkms build` compiles the HyperFlux driver and the Full OpenRazer driver against every kernel each release offers: Ubuntu's generic kernel, which is the only one Ubuntu 26.10 ships, Debian's stock and realtime kernels, Fedora's release and updates kernels, and openSUSE's longterm and default kernels. `modinfo` checks each module's vermagic, and every installed program is checked against the glibc that the release ships; on Fedora and openSUSE strong symbol references must also stay within the declared glibc floor, and the DKMS signing certificate must exist at `/var/lib/dkms/mok.pub`. Finally the packages are removed, including the stock OpenRazer service, and DKMS must no longer list either driver. The package files are kept as a workflow artifact for 14 days and are never published. Nothing is loaded and no device is touched.

## Checks Required Before Merging

- `Analyze (c-cpp)`
- `Analyze (python)`
- `Dependency review`
- `Distribution packages`
- `Documentation render`
- `Fast software`
- `Full software`

Branch protection: `solo-maintainer` with 1 trusted maintainer. Required human approvals: `0`; code owner review required: `false`.

With one maintainer, a required approval would be impossible, so none is required, but every required check must pass on the latest commit of the branch. Review by a second person becomes required once a second trusted maintainer is added. Nobody can bypass the branch rules. Release checks live in `assurance/release-gates.json` and CI never changes them.

## Issues, Pull Requests, And Labels

- CODEOWNERS names one owner for everything; a path gets its own rule only when someone else owns it.
- Issue forms ask for `hyperfluxctl doctor` output and the support bundle preview (the device support form also asks for `hyperfluxctl qualification --json`), ask people to remove private data first, and never suggest that anyone may send commands to their device.
- The pull request template is a short checklist: generated files, checks, docs, changes to the protocol, kernel interface, packages, or install behaviour, and private data.
- Dependency updates are grouped by GitHub Actions, Cargo, and each Python integration.
- Labels and the branch rules for `main` are generated from this repository and checked against GitHub.
